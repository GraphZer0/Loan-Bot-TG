Компоненты системы

LoanTelegramBot

Отвечает за взаимодействие с Telegram API.

Функции:

* получение сообщений пользователей и нажатий inline-кнопок;
* отправка ответов (текст и/или клавиатура);
* передача сообщений в обработчик.

⸻

BotMessageHandler

Реализует бизнес-логику пользовательского диалога.

Функции:

* обработка текстовых команд и нажатий inline-кнопок (handleCallback);
* прерывание диалога командой /cancel;
* нормализация числового ввода (запятая как разделитель дробной части);
* управление состоянием пользователя;
* формирование запросов к сервисам.

⸻

BotResponse / BotButton

Абстракция ответа бота, не зависящая от классов Telegram API: текст плюс необязательная inline-клавиатура (список рядов кнопок).

LoanTelegramBot сам отвечает за перевод BotResponse в SendMessage с InlineKeyboardMarkup — BotMessageHandler ничего не знает о конкретном способе доставки ответа пользователю (низкая связанность между бизнес-логикой и Telegram API).

⸻

UserSession

Хранит данные текущего диалога пользователя:

* сумма кредита;
* срок;
* ставка;
* тип платежа.

⸻

LoanService

Основной сервис приложения.

Функции:

* расчёт графика платежей;
* сохранение истории запросов;
* получение истории пользователя.

⸻

PaymentCalculatorFactory

Создаёт необходимую реализацию калькулятора.

Используется паттерн Factory.

⸻

PaymentCalculator

Интерфейс расчёта платежей.

Реализации:

* AnnuityPaymentCalculator
* DifferentiatedPaymentCalculator

⸻

LoanRequestRepository

Абстракция слоя хранения данных.

Позволяет заменить способ хранения без изменения бизнес-логики.

Реализации:

* InMemoryLoanRequestRepository — хранит заявки в памяти процесса, данные теряются при перезапуске (используется, если не задана переменная окружения DB_PATH);
* SqliteLoanRequestRepository — хранит заявки в файле SQLite (JDBC), данные переживают перезапуск процесса.

Main.java выбирает конкретную реализацию по наличию переменной окружения DB_PATH — остальной код (LoanService, AnalyticsService) работает только с интерфейсом и не знает, какое хранилище используется.

⸻

AnalyticsService

Сервис аналитики.

Функции:

* статистика по типам платежей;
* статистика по срокам;
* фильтрация заявок по сумме и/или типу платежа.

⸻

ManagerAuthService

Проверяет логин и пароль менеджера (переменные окружения MANAGER_LOGIN / MANAGER_PASSWORD).

Не хранит состояние авторизации — только сверяет переданные учётные данные.

⸻

ManagerSessionStorage

Хранит множество идентификаторов пользователей Telegram, прошедших авторизацию менеджера, на время работы процесса.

Отделён от UserSessionStorage: авторизация менеджера — самостоятельная область ответственности, не связанная с диалогом расчёта кредита.

⸻

MoneyFormatter

Форматирует денежные суммы с разделителем разрядов (например, "1 250 000") для читаемого вывода в Telegram.

Используется в PaymentScheduleFormatter и HistoryFormatter — единая точка форматирования сумм вместо дублирования логики в каждом из них.

⸻

Применение принципов SOLID

SRP

Каждый класс имеет одну ответственность.

Примеры:

* LoanTelegramBot — Telegram API.
* LoanService — расчёты кредита.
* AnalyticsService — аналитика.
* HistoryFormatter — форматирование истории.
* MoneyFormatter — форматирование денежных сумм.

⸻

OCP

Для добавления нового типа платежей достаточно:

1. создать новую реализацию PaymentCalculator;
2. добавить её в Factory.

Существующий код не изменяется.

Аналогично для хранилища: новую реализацию LoanRequestRepository можно добавить, не меняя LoanService и AnalyticsService.

⸻

LSP

Любая реализация PaymentCalculator может использоваться вместо другой.

Аналогично взаимозаменяемы InMemoryLoanRequestRepository и SqliteLoanRequestRepository — переключение между ними в Main.java (через переменную окружения DB_PATH) не требует изменений в остальном коде.

⸻

ISP

Интерфейсы небольшие и специализированные.

Пример:

PaymentCalculator
LoanRequestRepository

⸻

DIP

Сервисы работают через абстракции.

Пример:

private final LoanRequestRepository repository;

а не через конкретные реализации.

Используемые принципы разработки

DRY

Повторяющийся код вынесен в отдельные компоненты (например, форматирование сумм — в MoneyFormatter, используется сразу в двух форматтерах).

KISS

Архитектура максимально проста и понятна.

YAGNI

Реализован только необходимый функционал согласно требованиям проекта.
